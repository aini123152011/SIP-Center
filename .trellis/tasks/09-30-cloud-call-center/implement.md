# 执行计划 — 云呼叫中心与电销系统（M1-M4 并行轨道）

> 团队假设（D8）：10+ 人——语音 2 / 后端 4 / 前端 2 / AI 2 / 测试运维 1。
> 轨道并行：M1 与 M2 尾部重叠，M3 的管道部分自 M1 后期启动。总工期目标 ~6 个月到 M4。

## M0 技术预研（1-2 周，语音组，与 M1 重叠启动）

- [ ] FreeSWITCH 预研环境：安装物料（Dockerfile/compose）、SIP 中继模拟、WebRTC WSS 打通
- [ ] 呼叫压测基线：单节点 200 并发,记录 CPU/内存/RTP 质量（MOS/PESQ），产出调优笔记
- [ ] `mod_audio_stream` 音频帧管道 PoC：延迟实测数据（ASR 输入路径）
- [ ] JeecgBoot 多租户 PoC：租户隔离深度/配额/线路池可行性结论（不达标 → 自研租户模块决策）

## M1 语音底座（~2 月，语音组 + 前端 1 + 后端 1）

- [ ] Monorepo 初始化：`backend(biz-plane) / voice / ai / frontend / deploy` 目录与 CI 流水线（构建/单测/lint）
- [ ] JeecgBoot 引入 + 裁剪（移除无关 demo）+ 安全加固基线（默认密钥/Druid 端点/注入项清单逐项关闭）
- [ ] 数据库基线：Flyway 接入，全表 `tenant_id` 规范 + 租户插件 + 线路/号码/配额资源池模型
- [ ] voice-plane 服务骨架：Netty ESL 客户端、呼叫状态机、坐席状态机（空闲/小休/通话/话后）
- [ ] ACD 排队（技能组路由 v1）+ IVR DSL 引擎 v1（节点/分支/变量槽/转人工）
- [ ] 软电话组件：JsSIP + WSS，签入签出/就绪/小休、呼入接听、点击外呼、挂断/保持/转接
- [ ] 录音管道：录音写对象存储、CDR 落库、Kafka 通话事件发布
- [ ] 弹屏链路：事件 → biz WebSocket → 坐席工作台弹屏（客户匹配 v1）
- [ ] 监控基线：Prometheus + Grafana（语音指标：并发/接通率/掉话率）

**M1 验收**：新坐席 10 秒内签入并接听经 IVR/ACD 分配的来电；全程录音可检索回放；200 并发压测 30 分钟丢话率 0、无 OOM；事件流可按租户查询。

## M2 电销闭环（~2 月，与 M1 尾部并行，后端组 + 前端 1）

- [ ] dialer 框架：任务/名单/重拨规则，策略接口抽象
- [ ] manual/preview 策略 → progressive 倍率拨号 → predictive（实时统计滑动窗口 + 弃呼率护栏 + 降速开关）
- [ ] compliance 强制前置：黑名单/频控/投诉名单过滤环（dialer 策略不可绕过）
- [ ] 客户管理：档案/联系人/跟进记录/名单导入分配/公海回收
- [ ] 产品管理：商品/价格体系 CRUD
- [ ] 订单管理：状态机手写（created→paid→shipped→signed→settled/售后），弹屏成交联动
- [ ] 报表 v1：通话量/接通率/坐席绩效/弃呼率（PG 起步，ClickHouse 预留）

**M2 验收**：1000 名单导入 → progressive 自动外呼 → 接通 5 秒内分配坐席并弹屏；predictive 运行 1 小时弃呼率 ≤ 配置阈值（默认 3%）且报表可查；弹屏下单全状态流转审计可查。

## M3 AI 全量（~3 月，管道自 M1 后期启动，AI 组）

- [ ] media-stream 生产化：FS → WS 音频帧分发（双声道、断线重连、背压）
- [ ] asr-gateway：FunASR 自托管集群接入 + 适配器接口 + 延迟指标；云 ASR 适配器备选实现
- [ ] bot-engine：话术 DSL 编排器（版本发布/沙箱试运行）+ LLM 兜底（langchain4j，OpenAI 协议兼容）+ TTS 适配 + barge-in
- [ ] 转人工闭环：机器人 → ACD 注入（携带对话上下文）→ 坐席侧展示完整历史 + 实时字幕
- [ ] 坐席辅助：实时字幕 + 话术推荐 v1（规则引擎起步）
- [ ] qa-engine：CDR 触发离线转写 → LLM 评分/违规检测 → 质检报告 + 申诉复检流

**M3 验收**：机器人通话端到端应答延迟 P90 ≤ 1.5s，支持 3 次以内打断不串话；100 条历史录音质检跑通并生成评分报告；转人工后坐席可见完整对话链。

## M4 商业平台（~2 月，后端组 + 运维）

- [ ] 多租户增强：套餐/配额/计费账单（通话分钟/坐席数/线路维度）
- [ ] License 机制：机器码绑定 + 离线激活 + 功能开关 + 超期降级
- [ ] 私有化交付物：compose 拓扑（1 台/3 台）、安装升级脚本、Flyway 回滚验证、交付验收清单
- [ ] 财务深化：收款/退款/对账批次 + 开票对接（金税接口）
- [ ] 物流深化：快递100/快递鸟聚合（运单创建/轨迹回传/电子面单）
- [ ] 运维面板：告警规则基线（通话质量/队列堆积/Kafka 延迟/磁盘）

**M4 验收**：全新 Ubuntu VM 执行安装脚本 ≤30 分钟出可用实例，License 离线激活与超期降级正确；SaaS 租户全流程（创建→套餐→通话→账单）金额一致；JimuReport 类闭源组件已完成再分发合规核查或替换。

## 验证与回滚

- 每里程碑收尾：`trellis-check` 全量检查 + 压测基线对比（不劣化上一里程碑）+ Flyway 迁移回滚演练
- 语音/业务/AI 三单元独立版本号，支持单独回滚
- 合规红线检查项纳入 M2/M3 验收（弃呼率、频控生效、录音留存策略）

## 里程碑依赖

- M2 dialer 依赖 M1 的呼叫状态机与事件流；M3 管道依赖 M1 录音/事件基础设施；M4 计费依赖 M1 资源池模型 + M2 话单数据。
- M0 PoC 结论是 M1 内"自研租户模块 vs JeecgBoot 原生"的决策输入，必须在 M1 第 2 周前关闭。
